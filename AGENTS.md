# Agent instructions

These instructions apply throughout this repository. Read `README.md` for setup, gameplay and the simulation's data boundaries before changing the app.

## App architecture

11–0–0 is a fantasy Chess Olympiad game with a browser ES-module UI and a shared historical rating catalogue. Local development uses Node.js 22.13 or newer and built-in SQLite without runtime packages. Hosted Sites uses an isolated Vinext adapter and Cloudflare D1.

`dist/` contains the maintained browser source. Edit its top-level files directly. Sites builds generate only `dist/server/`, `dist/client/` and `dist/.openai/`; never replace or clean the entire directory. Local development and Sites use `/api/catalog`. The separate static builds export the same SQL catalogue to `release/pages/catalog.json` or `release/cloudflare/catalog.json` and use an explicit relative catalogue URL; static hosting must serve the corresponding generated release, not the maintained `dist/` source.

### State and data flow

- The page loads `app.js`, fetches the `catalogue-url` meta value (`/api/catalog` by default; `./catalog.json` in Pages releases), configures engine indexes, then creates `initialState()`. Catalogue failures show a retry view rather than stale placeholder players. Keep API and static exports identical, including source citations, canonical identities and the catalogue release.
- The UI attempts to restore JSON from local storage under `11-0-0:save:v4`, restoring it through pure `restoreSave` and validating it with `validSave`. Current simulation rules are `olympiad-8`, with `era-balanced-1` appended to the rules fingerprint. Earlier rating/simulation rules cannot upgrade in place because arithmetic and field allocation changed. Back up incompatible active/completed saves before a fresh draft; independent Best-run reports remain readable.
- Game state progresses through `draft`, `tournament` and `results`. UI event handlers apply engine functions, then render and save the state.
- Quick Sim completes the draft and all eleven rounds through the existing engine rules and reserve planner. Preserve existing picks, outstanding offer assignments and starting profiles; do not mutate the input draft or overwrite it before success. Quick Draft shares `completeDraft`; seeded `quickSim` reproduces the same squad and tournament for identical inputs. Its UI busy state is transient and its results use the normal save shape.
- Selection, busy flags, the viewed round and the chosen results view are transient UI state, separate from the saved game.
- Appearance uses a separate `11-0-0:theme` preference (`light` or `dark`); follow system changes until an explicit choice is saved and sync that choice across tabs. The head script applies the initial palette before paint; `app.js` connects the accessible header toggle before fetching the catalogue, including loading and failure views. Keep surface and foreground tokens distinct so dark mode preserves contrasting squad text and readable reports, dialogs and status labels.
- Best runs use a separate `11-0-0:best-runs:v1` browser key, keeping three completed reports ranked by match points, wins, finishing place, SB and board points, with earlier exact ties retained. Capture every completion path and the existing completed save on load without duplicate entries. Copy player/source details, starting profiles, final readiness, all 11 user match reports, all team scores and final standings so records survive catalogue/rules changes independently of active-save validation. Viewing records must never replace or mutate the active game. Preserve unreadable history under its backup key before replacing it; show storage failures. The separate history version describes report structure, not simulation rules.
- Match-report performance breakdowns use native keyboard-accessible disclosures and never change saved state. Keep source/effective ratings, traits and readiness visible, and show all modifier calculations directly in pre-match forecasts. Trait symbols and form/fatigue colours supplement readable labels. Keep draft controls before the lineup in reading and keyboard order, round actions above reports, and compact standings directly beneath reports in the same column. Mobile draft boards use two columns; never clip their profiles or hide any of the five offered players.
- Match previews and board-order dialogs use the wider planning layout, with explicit piece-colour labels, visible opponents and readable probability labels beside decorative bars. Board-order controls retain native selects and adjacent move buttons, preserve keyboard focus after changes and keep the reserve separate. Projected board points are the sum of board expectations for the visible lineup, not a guaranteed match result.
- Draft offers use `Math.random` by default. Every eligible country-year has positive weight `2 ** ((strength − 2600) / 50)`, where strength averages the eligible leader and eligible top-three mean; preserve full top fives and canonical-person exclusion. Quick Draft and Quick Sim use shared `rankedCandidates`/`draftValue` estimates over eleven rounds, including reference trait/style effects, fatigue/recovery, decaying starting form and integrated consistency swings. Keep `DRAFT_RULESET` in the save fingerprint. Tournament simulation uses a stored seed and round number; preserve reproducibility for identical inputs and rotation decisions.
- Game saves carry catalogue, trait and profile rules versions. Preserve version-1 through version-3 saves under their original keys; back up incompatible or malformed version-4 saves before replacing them.
- Call shared fixed abilities career traits; reserve signature for an ability unique to exactly one player. Famous career traits use exact canonical person IDs and cited recurring career characteristics. Unprofiled players roll 25% no trait, otherwise uniformly among all traits, once per draft offer; retain the picked assignment. Never reroll during render or reload. Opponents use separate seeded assignments fixed for their tournament. Random traits and numerical tradeoffs are game data, not biographical facts; see `data/traits.md`.
- Individual trait modifiers use `TRAIT_BONUS_CAP` (80 in `career-traits-5`); preserve specialist conditions, counter interactions and documented tradeoffs. Generalists receive a smaller constant bonus. Defender strength changes smoothly with the rating gap rather than jumping at a threshold. Keep numerical descriptions and tests aligned with the pure effect resolver.
- Maintain sourced fixed career traits for recognizable players, including everyone with a sampled catalogue edition with a source rating at least 2750. This coverage floor does not justify inventing a trait from rating alone. Retain qualifications about evolving styles and young players' careers so far. The current 115 career traits share fixed profile presets across editions and opposing teams; expanding assignments requires a trait rules version bump and deliberate save handling.
- Both sides use the same trait, style, stamina, form and consistency rules. Famous profiles use fixed game-archetype presets; unprofiled players roll them per offer, and everyone rolls starting form. Numerical profiles are game values, not sourced personal qualities. Retain immutable starting profiles separately from each team's current form. The user acts as captain through lineup and reserve decisions. Do not add captain attributes, selected captains, staff slots or leadership bonuses to either side.
- Match forecasts must be pure and match the subsequent simulation for identical inputs. Daily performance depends only on seed, round, team and player; board moves cannot reroll it. AI reserves consider fatigue and form under the same rules used for user lineup recommendations. Era-balanced game ratings determine initial and AI board order. The user may freely permute the four active boards between rounds through `setBoardOrder`; keep the reserve separate and save the chosen order. Manual substitutions insert the reserve into the exact vacated slot. Keep source Elo separate from every game modifier. Bump `TRAIT_RULESET` or `PROFILE_RULESET` as appropriate and deliberately handle saves after rule changes. Validation checks temporal form/fatigue history as well as effect arithmetic.
- Simulation rules have their own `SIMULATION_RULESET` included in the saved rules fingerprint (`olympiad-8`). Board expected scores use shared `ELO_SCALE` (320), with a 28-point White advantage; preserve expected score when applying draw modifiers. Forecasts, planners, draft estimates, save validation and audit probability checks must use the same curve. Immutable `seedingRating` uses the roster's best four era-balanced game ratings for pairings and standings; `rating` remains the current lineup's display average. Round fixtures derive colours from played team/player histories and neutral readiness projections of the next four; individual imbalance and repeated colours take priority over the team’s first-board pattern. Reconstruct temporal forms/loads when validating historical colour choices. Derive conditions/outcomes from independent fixture/board seeds. Substitutions and board permutations must preserve fixtures and unrelated matches. Neutral fixture projections must never use proposed manual orders; pass a preferred lineup only to user recommendations and include it in planner cache keys. Validation accepts arbitrary user board order in current and historical lineups, while checking AI source order and all readiness/context arithmetic. Validate historical colour/context rules and never use a proposed lineup to regenerate fixture conditions.
- Fatigue load is an integer 0–100 on every team's player maps, distinct from consecutive-game streaks. Playing adds `14 − stamina`; sitting out removes 30. Load above 24 costs 0.5 Elo per point (maximum 38), halved for grinders. Form is 6 Elo per level; consistency 1–5 limits daily swings to ±16, ±12, ±8, ±4 and ±2. Share `SWINGS` between simulation and draft estimates. Profile rules are `squad-profiles-4`. Only playing a round updates load. Previews, substitutions and lineup recommendations are pure with respect to load. Validate the complete load history and preserve incompatible saves before a fresh draft.
- Opponents plan all five possible reserves over up to three remaining rounds using expected match points, current traits/styles, workload and form. Evaluate current fixture matchups against a neutral projection of the opposing lineup, independent of user substitutions; future rounds use averaged reference effects. User recommendations use the visible planned opponent. They must not peek at future results or daily swings. Use the same planner for user recommendations and Auto-rotate & finish, preserving the user’s selected order and replacing a rested player in that exact board slot. Manual round play preserves the full selected lineup. Future neutral planning depends on the active player set, not proposed board permutations. Opponent roster dialogs show the next planned lineup and fatigue; completed tournaments show the final lineup.
- There are no application accounts or remote game saves. SQL stores the shared player catalogue.
- Eight fictional Legends offers contain the strongest forty distinct sampled pre-1927 editions from 43 checksum-pinned Chessmetrics tables. Keep actual edition years and per-player sources; no national affiliation is inferred. Exclude Legends from national opponent allocation, preserve canonical identity across later editions and retain all five candidates when one becomes ineligible. SQL snapshot kind distinguishes collections from country snapshots.
- Country snapshots use period federation and the top five published standard ratings, independent of Olympiad participation. Show all five; disable ineligible picks. Prevent drafting the same person from multiple years.
- Tournament opponents are the strongest 49 all-time A/B lineups by unrounded era-balanced four-board total, plus the user's team for 50 total. For each person keep their best observed era-balanced country edition (ties: latest year, federation, edition ID), using its federation. Each federation's first five form A and the next five B. Never repeat a person across opposing teams or combine Russia and the Soviet Union. Source coverage is selective; do not describe sampled ratings as exhaustive career peaks.
- Official-list coverage is 1972–2026 at two-year intervals (July 1972, May 1974, otherwise January). Twenty-two audited source Chessmetrics country snapshots cover 1927, 1928 and every even year through 1970 except 1944; its original estimate table is retained but remains an explicit affiliation-audit gap. Their country coverage is selective and each has a complete higher-rank affiliation audit. Additional early countries remain unavailable pending evidence; never publish speculative top fives. Preserve temporal inference qualifications and sourced person-identity crosswalks.
- Preserve source date, URL, SHA256 and raw ratings. The main game uses `era-balanced-1` in both Classic and Expert; no extra rating mode exists. `rawRating` preserves the source, `eraAdjustment` records the capped ±150 rank mapping to January 2026, and `rating` is the game base. Match `baseRating` is that game base; effective `rating` adds traits/style/form/daily swing and subtracts fatigue. Keep a visible fictional-balance disclaimer and source/game/effective breakdowns. Use game ratings consistently for drafting, lineup order, seeding, national field selection, forecasts, planners and simulation; keep country top-five membership and eligibility source-based. Country-year rolls must contain at least one player with a source rating strictly above 2650 (2650 is excluded, 2651 qualifies); preserve the complete top five of each qualifying snapshot.

- Match preparation combines board order, reserve selection, shared planner advice and full forecasts in one responsive dialog. The projected board-point change compares the current lineup with the lineup when the dialog opened; it never rerolls the fixture or mutates fatigue. Recommendations show neutral-performance current-round match expectations alongside their recovery horizon.
- Draft comparisons reuse `draftValue` only in Classic and retain the original offer assignments; Expert must never expose a rating-derived rank or estimate in this view.
- Portable imports preview before replacing active progress, back up existing browser data and merge reports through `keepBestRuns`. Incompatible games are never restored; independent valid reports remain importable. Serialize active-save writes with a shared Web Lock where supported, compare the stored base before writing, pause stale tabs and allow export/reload. Unchanged renders must not write storage. Never replace an incompatible/malformed save if preserving its backup failed.
- Offline preparation must cache a complete hash-verified app/catalogue cohort, isolated by origin path. Generate the worker from maintained `dist/sw.js` without modifying that template; preserve API/static catalogue parity and relative subpath URLs. Do not activate waiting workers during play without the user choosing the update. New browser assets belong in the shared allowlist and static-release assertions.

## Implementation guidance

- Keep orchestration in `engine.js`, pure trait definitions/effects in `traits.js`, browser APIs in `app.js`, and database access in `server/` or the hosted API adapter.
- SQLite and D1 share the generated schema and atomic seed logic. Keep migrations schema-only, immutable after application, and separate from data imports. Do not create migration-owned tables in request handlers.
- Keep local and hosted catalogue shapes consistent. Source updates must replace stale rankings atomically and advance the catalogue release. Identity crosswalks are source-name-qualified, preserve namesakes/reused IDs, and are included in the release fingerprint. Bump the selection-policy marker when changing field-generation rules.
- After schema changes, run `npm run db:generate` and commit the SQL, Drizzle snapshot and journal together.
- Follow the existing ES module structure. Add dependencies or build tooling only when the task requires them.
- Preserve draft constraints: five unique players, with four active boards and one reserve. Preserve the eleven-round, 50-team tournament unless the task changes those rules.
- When changing saved state, update validation and deliberately handle existing saves. Keep `SAVE_VERSION` and the UI storage key consistent with the chosen compatibility strategy.
- Escape user-controlled values before inserting them into HTML. Preserve keyboard access, dialog focus, reduced-motion support and responsive layouts when changing the UI.
- Preserve local font licenses and update `README.md` and this architecture guide when relevant behavior, file responsibilities or commands change.
- Inspect the working tree before editing. Preserve unrelated user changes and include only task-related changes in commits.

## Validation

Run commands from the repository root:

```bash
npm start       # Same server as npm run dev; http://localhost:4173
npm run check  # Syntax checks for application, server, script, test and backend modules
npm test       # SQL catalogue, rules and fast simulation tests
npm run test:full # Complete 100-tournament simulation and full test suite
npm run build  # Hosted Worker/assets; requires npm --prefix backend ci
npm run build:pages # Static release/pages/; no backend dependencies or remote database
npm run preview:pages # Static-only http://localhost:4174/11-0-0/; PAGES_BASE_PATH and PORT configurable
npm run build:cloudflare # Static release/cloudflare/; no backend dependencies or remote database
npm run preview:cloudflare # Static-only http://localhost:4175/; PAGES_BASE_PATH and PORT configurable
npm run package:cloudflare # Rebuild and ZIP for dashboard upload; Python 3 standard library
```

For catalogue changes, test SQLite persistence, foreign keys, complete source-ranked top fives, known modern rosters, unchanged ratings, the strict source-rating cutoff above 2650, all-time A/B selection, cross-era identity links and atomic release replacement. For engine changes, run the syntax checks and engine suite; add or adjust tests for changed behavior. The suite covers 1,000 drafts, 100 complete tournaments, deterministic results, scoring, pairings, fatigue, invalid actions and saved-game validation.

For UI changes, run syntax checks and verify the affected browser flows at desktop and mobile widths. The optional full browser QA setup and environment overrides are documented in `README.md`. For documentation-only changes, verify commands, file paths and statements against the source, and check the diff for whitespace errors with `git diff --check`.

For Pages changes, run the static export integration tests and affected builds. Verify both root and repository-subpath previews, relative catalogue/assets, no backend requests, save persistence and catalogue-failure recovery; see `docs/github-pages.md` and `docs/cloudflare-pages.md`. For Cloudflare, also check `_headers` and nested 404 recovery with Wrangler. Keep its Wrangler config isolated under `cloudflare/` and use `--cwd cloudflare` so Sites cannot discover it. Keep the static catalogue identical to the SQL API and preserve source/font licenses. Do not change the existing Sites identity or D1 configuration for a Pages release.

## Task and commit workflow

- Split each task into appropriate, focused commits. A small cohesive task can use one commit; separate independent concerns into distinct commits.
- Each commit should represent one reviewable change. Keep its implementation, relevant tests and accompanying documentation together, and keep intermediate commits working.
- Validate each logical change before committing. Review the diff and stage only the files or hunks belonging to that commit.
- Write every commit message in the exact form `action: message`. Use a lowercase action such as `add`, `fix`, `refactor`, `docs`, `test`, `style` or `chore`, followed by a colon, one space and a concise description. Use imperative wording for the description.
- Report the completed changes and validation, including any checks that could not be run.

Examples:

```text
add: support reserve rotation between rounds
fix: preserve the selected draft slot after a reroll
refactor: isolate tournament pairing rules
docs: describe app architecture and contribution workflow
test: cover invalid saved tournament data
```
